# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Stack

Next.js 15 (App Router) + React 19 + TypeScript + Tailwind v4 + Framer Motion + lucide-react. `output: "standalone"` for the production Docker image.

## Commands

```bash
npm install                 # install deps
npm run dev                 # dev server (default port 3000)
npm run build               # production build (verifies TS + Tailwind)
npm run start               # serve production build
npm run lint                # eslint
npm run typecheck           # tsc --noEmit
npm test                    # vitest: tests/ (lógica de servidor: actions, feeds, dates, telegram, rate limit, JSON-LD)
```

CI runs all four plus `npm audit --omit=dev --audit-level=critical` and the build (the level is `critical` because Next 15.5 nests a build-time-only postcss with a `high` advisory that only Next 16 fixes; lower it to `high` after that migration). Node **22** in both the Dockerfile and `ci.yml` (Node 20 is out of support since April 2026); keep them in sync.

If `npm run dev` (and `npx next ...`) returns a truncated "Errors: 1 | Warnings: 0" summary, the npx wrapper is swallowing output — call the binary directly: `./node_modules/.bin/next dev`.

`next dev` and `next start` share `.next/`: do not run both at once. The CSP adds `'unsafe-eval'` to `script-src` in development only (`next.config.ts`): Next's HMR evaluates code and without it the dev page never hydrates (everything animated stays invisible). A local `next build` reuses `.next/cache/fetch-cache`, so the prerendered feeds can be weeks old; delete that folder to see current data (the Docker build always starts clean).

## Architecture

Single long-scroll landing page modeled after the **DJSwarthy Academy** reference site (`https://fictional-octo-guacamole-rose.vercel.app/`). The visual identity (palette, typography, gradient, glow, structure) is copied from that reference; the content is rewritten as an **artist presentation site** (booking, sets, fechas) instead of a course landing.

- `app/page.tsx` — async server component that fetches the YouTube + SoundCloud feeds (`lib/feeds.ts`) and the Spotify discography (`lib/spotify.ts`) with `Promise.allSettled` (a fetcher that throws degrades to `[]`/`null` instead of taking the home down) and composes the sections in order: Hero → Stats → Dates → Venues → Mixes → Formats → About → Releases → Testimonials → Faq → FinalCta → Contact → Socials. The order follows the promoter's funnel (listen and see where he has played, understand what they buy, clear doubts, ask for a date); Contact goes after the booking form so nobody uses the generic form to book (it collects no date or city). The navbar links follow the same order. `export const revalidate = 3600` pins the home as static + hourly ISR; **never add `cache: "no-store"` to a fetch reached from this page** (it turns the route dynamic, which is what the Spotify token POST used to do). Reorder by editing this file alone; sections do not depend on each other (FinalCta embeds BookingForm). `Dates` and `Testimonials` render nothing while `site.dates` / `site.testimonials` are empty. The feeds are classified once here with `splitMixes()`: sessions go to `Mixes`, productions to `Releases`, and the number of sessions on the page to `Stats` (it replaces the stat marked `live: "sessions"` in `site.stats` when there are at least 10; otherwise the static figure stays).
- **Animation architecture.** `components/motion/MotionProvider.tsx` wraps the app in `LazyMotion` (features loaded from `components/motion/features.ts` in a separate chunk, `strict` mode) + `MotionConfig reducedMotion="user"`. Use `m` from framer-motion, **never `motion`** (strict mode throws). Purely presentational sections (Hero, Stats, About, Dates, Mixes, Releases, Formats, Venues, Testimonials, Socials, FinalCta) are **server components** that wrap animated nodes in `components/motion/Reveal.tsx`; only Faq, Contact, BookingForm, BookingLink, Navbar, StickyCta, NowPlaying, MediaFacade, MixLibrary, SpotifyProfilePlayer and the press-kit widgets (`components/PressKit.tsx`) are client components. This keeps `lib/data.ts` out of the client bundle (home route 19.4 kB, First Load JS 131 kB). **Never import `lib/data.ts` from a client component**: one import drags the whole content object (bios, rider, FAQ) into the JS. Client components get what they need as props from their server parent (`Faq` receives `items`, `SpotifyProfilePlayer` `artistId`, `BookingForm` `formats` and `email`). The Hero animates with the CSS class `fade-up` instead of Framer so the above-the-fold copy paints without JavaScript. Its composition mirrors the social image (`app/opengraph-image.tsx`), so what people see when the link is shared matches what they land on: the artist name is the `h1`, the slogan goes under it and the copy is left-aligned from `md`, leaving the portrait clean (right on desktop, top on mobile) with no text over the face. The portrait is the LCP element and carries `priority` (lazy-loaded it cost ~1 s of LCP on desktop); the per-breakpoint `max-w-*` on the paragraph and the genre chips keep the copy off the face on tablets. Primary CTA: "Solicitar fecha" (`#booking`).
- `components/Overline.tsx`, `components/SectionHeading.tsx`, `components/NewTabHint.tsx` — shared section header pieces (the decorative ★ is `aria-hidden`) and the screen-reader-only "(se abre en una pestaña nueva)" hint every `target="_blank"` link must carry.
- `components/forms/primitives.tsx` — shared form pieces (`inputClass`, `Honeypot`, `FormError` with `role="alert"`, `FormSuccess` which takes focus on mount, `SubmitButton` with `aria-disabled`, `field()` to read FormData as string). Both forms wrap the server action call in try/catch so a thrown action still shows an error. The booking form asks first for what defines the gig (date, city, event type, optional set format, venue/event name, time slot) and then for who asks; budget is free text because the fee bands are not fixed yet. BookingForm sets the date `min` in an effect (computing it during render caused a hydration mismatch). The form is split into three `fieldset`s (the event, your details, optional details). `tipoEvento` and `formato` are controlled selects so `components/BookingLink.tsx` can preselect them: "Solicitar este formato" and "Contar mi evento" dispatch a `booking:prefill` DOM event before jumping to `#booking` (not a search param: `useSearchParams` would opt the form out of prerendering). The format options come from `site.formats[].option`. Nothing the visitor types is sent to analytics: `lib/analytics.ts` only reports that a form was sent or a player opened (Plausible custom events "Booking enviado", "Contacto enviado", "Reproducir"; each must be created as a goal in the Plausible dashboard to show up).
- `lib/site.ts` — `SITE_URL`, `SITE_NAME`, `OG_IMAGE` and `CONTENT_UPDATED_AT` (feeds the sitemap `lastModified`; bump it by hand when copy changes). Import from here, not from `lib/json-ld.ts`, when you only need the URL.
- `app/opengraph-image.tsx` — generates the 1200×630 social image at build time with `next/og` (dark background, "DJ SWARTHY", slogan, portrait from `public/images/og.jpg`). The brand font is vendored in `assets/fonts/BebasNeue-Regular.ttf` (OFL) because `next/font` is not available inside `ImageResponse`. Do not declare `openGraph.images` in `layout.tsx`: the file convention wins.
- `app/not-found.tsx`, `app/error.tsx`, `app/manifest.ts` — branded 404, client error boundary and web manifest. Icons (`public/apple-touch-icon.png`, `icon-192/512.png`, `icon-512-maskable.png`) are the isotype inverted onto `#0a0a0a`, generated once with sharp.
- `app/privacidad/page.tsx` — GDPR privacy policy. It is the legal basis for the two forms, both of which require an explicit consent checkbox (`components/ConsentCheckbox.tsx`) that the server actions re-validate.
- `app/press-kit/page.tsx` — EPK: short/long bio in Spanish and English with copy buttons (`components/PressKit.tsx`; the English bios in `site.press` are translations of the Spanish ones and must change with them), last-updated date (`CONTENT_UPDATED_AT`), quick facts, listening links, technical rider and downloadable artwork with previews, all driven by `site.press`. "Imprimir o guardar en PDF" relies on the `@media print` block of `globals.css`, which flips the colour tokens to ink on white without touching the components; the chrome and every button carry `print:hidden`. Browsers do not print backgrounds by default, so `text-gradient` gets a solid colour in print; that override must live in `@layer utilities` next to the utility (from `base` it cannot beat it).
- `lib/dates.ts` — `upcomingDates(now?)` drops past gigs and sorts ascending, comparing ISO day strings in **Europe/Madrid** (`todayIso()`), so the container's UTC clock never shifts a gig by a day. Also exports `isIsoDay()` (used by the booking action to validate the event date). Shared by `app/page.tsx` and `lib/json-ld.ts` so the agenda and the `MusicEvent` schema never disagree. `Dates.tsx` formats with an explicit `timeZone` for the same reason.
- `app/layout.tsx` — loads two Google fonts (`Bebas Neue` → display, `Inter` → body) and exposes them as `--font-bebas` and `--font-inter`. Also carries the SEO surface: metadata + OpenGraph/Twitter text (the image comes from `app/opengraph-image.tsx`), JSON-LD and the Plausible analytics script (`data-domain="djswarthy.es"`). The only `preconnect` is Plausible: the players are facades and thumbnails go through `/_next/image`, so preconnecting to YouTube/SoundCloud was wasted work.
- `lib/json-ld.ts` — `buildJsonLdString(now?)` builds the graph (`MusicGroup`, `WebSite`, `Service`, `FAQPage` from `site.faq`, one `MusicEvent` per upcoming gig) **per render** (a module-level constant froze the event list at process start) and escapes `<` so no copy can close the `<script>` tag.
- `app/actions/booking.ts` / `app/actions/contact.ts` — server actions that forward form submissions to a Telegram chat via `lib/telegram.ts` (needs `TELEGRAM_BOT_TOKEN` + `TELEGRAM_CHAT_ID` env vars). They are public endpoints, so every field goes through `cleanField`/`cleanLine` (non-strings become `""`, single-line fields lose newlines so nobody can forge a "Responder a:" line), consent must be `=== true`, the booking date must be a real ISO day ≥ today in Madrid, and honeypot (`web`) submissions are silently accepted. `sendTelegramMessage` has a 10 s timeout, logs only the HTTP status (never the body or the URL, which carries the token) and truncates with `truncateHtml` so a cut never splits an entity or leaves `<b>` open. `lib/rate-limit.ts` trusts **only** `X-Real-IP` (nginx sets it); `X-Forwarded-For` is ignored on purpose.
- `lib/feeds.ts` — regex-parses the public YouTube and SoundCloud feeds (no API keys). Every fetch has an 8 s `AbortSignal.timeout`, bodies are capped, ids are validated against the platform's format before they reach an iframe `src`, and each feed returns at most `FEED_LIMIT` (30) items: a defensive cap, not what gets rendered (that is decided by `lib/mixes.ts`). It has to be generous: on SoundCloud the hour-long sessions sit behind the latest productions, and with the old cap of 8 none of them reached the page. Sends a browser User-Agent because YouTube 429s datacenter IPs otherwise. `getLatestYouTubeVideos()` **merges two sources**: the channel's `/videos` tab (the `ytInitialData` JSON scraped from `youtube.com/@swarthy_dj/videos`: long-form videos only, with duration and relative age, up to 30) is the list, and the RSS only adds the exact date to the uploads it knows. The RSS alone is not enough: it covers the last 15 uploads *including Shorts*, which are most of this channel, so as the only source it left the section with three sets; and YouTube already retired it once, so nothing may depend on it. If the page scrape fails the RSS is served without durations, with Shorts dropped *before* the cap. Durations come from the thumbnail badge (YouTube) and `itunes:duration` (SoundCloud). The thumbnail is the one the JSON declares for each video, without its signed query string: most have `hq720.jpg`, but a video not uploaded in HD only has `hqdefault.jpg`, and asking blindly for the 720p one left that card with a broken image. The relative age ("hace 2 meses", `VideoItem.publishedLabel`) is recognised by its text, never by its position: the views part carries an accessibility label too, and picking "the first labelled part" rendered the view count as the date. Returns `[]` on any failure; `Mixes` falls back to plain channel links. `lib/mixes.ts` classifies the items: `isSet()` goes by duration (10 minutes or more is a session; the title heuristic is only the fallback when a feed gives no duration), `mixStyle()` derives a style family from the title (trance / clásicos y remember / house / otros) and `toMixCard()` flattens each entry into the serialisable `MixCardData` that the cards render, with dates already formatted on the server. The two featured cards are always sets (newest of each platform, or two of one if the other has none) because the hero CTA promises "último set"; the remaining sets (up to `SETS_LIMIT`) go to `components/MixLibrary.tsx`, a client grid filterable by style, and the productions and covers (up to `PRODUCTIONS_LIMIT`) to the `Releases` section. `components/MixCard.tsx` is the shared card: a compact row on mobile that becomes a column through `has-[iframe]` when its player mounts. Every player is a **facade**: the thumbnail is a button and the `<iframe>` is only mounted on click, so YouTube/SoundCloud third-party cookies are never set on a plain visit. YouTube serves thumbnails from `i.ytimg.com` *and* `i1/i2/i3/i4.ytimg.com`, hence the `*.ytimg.com` `remotePattern` in `next.config.ts`.
- `lib/spotify.ts` — public artist data for `site.spotifyArtistId`. Two paths: the official Web API via **Client Credentials** (`SPOTIFY_CLIENT_ID` + `SPOTIFY_CLIENT_SECRET`) to list albums and singles with artwork, and the credential-free **public oEmbed** for the artist's name and photo. Without credentials it returns `[]` and `Releases` falls back to the profile player, which already lists the top tracks. The token is cached in module memory because a POST `fetch` never enters Next's Data Cache.
- `components/MediaFacade.tsx` — the facade shared by `Mixes` and `Releases`: a clickable cover (16:9 or 1:1) that only mounts the `<iframe>` after the click (and moves focus to it), so YouTube/SoundCloud/Spotify never set third-party cookies on a plain visit. Any new player must go through it. Only one player can be open: `components/ActivePlayer.tsx` (provider in `app/layout.tsx`) keeps the active one, and opening another unmounts the previous iframe so two mixes never sound at once. `usePlayer()` (same file) is the per-player hook shared by `MediaFacade` and `SpotifyProfilePlayer`; a player that unmounts while active releases the group. `components/NowPlaying.tsx` shows a floating bar (title, "Ver", close) while the open player is off-screen, so someone who pressed play and scrolled on can stop it or go back; it finds the player by its `data-player` attribute, sits under the header so it never collides with `StickyCta`, and is rendered before the page content so its two buttons come first in the tab order. It does not say "sonando": the player lives in a third-party iframe and the page cannot know whether it was paused inside. `components/SpotifyEmbed.tsx` is the plain iframe; `components/SpotifyProfilePlayer.tsx` is the client fallback card.
- `components/sections/Releases.tsx` — the `#spotify` section, all of his own music: a grid of Spotify releases with a per-album embed (or the artist profile player as fallback) plus the "Producciones y versiones" grid with what the YouTube and SoundCloud feeds bring that is not a session.
- `app/sitemap.ts`, `app/robots.ts`, `app/api/health/route.ts` — sitemap (home + press kit, `lastModified` from `CONTENT_UPDATED_AT`; `/privacidad` is `noindex` and left out), robots (disallows `/api/`), and the healthcheck endpoint used by docker-compose.
- `docs/AUDIT_PROMPT.md` — reusable prompt to run a multi-agent audit (security, a11y, SEO, React/perf, infra) and apply the findings on a branch.
- `docs/DESIGN_PROMPT.md` — reusable prompt for a design/product review from the point of view of a web designer for professional DJs (promoter booking funnel, music experience, EPK, copy, benchmark against other DJ sites), within the locked visual direction. Produces a report; changes only after the user picks them.
- `app/globals.css` — Tailwind v4 `@theme` block declares the design tokens. Renaming a token here renames the utility class everywhere. Custom utilities defined in `@layer utilities` are the brand primitives:
  - `gradient-primary` — the rojo→naranja diagonal gradient (`#e11d48 → #f97316`) used on CTAs, badges, step circles, value-stack footer.
  - `text-gradient` — same gradient applied to text via `background-clip: text`. Used on every section heading's accent word.
  - `gradient-glow` / `gradient-glow-orange` — the radial red/orange halo used as ambient background glow behind hero, contact and final CTA.
  - `shadow-glow` / `shadow-glow-strong` — the colored drop-shadow under primary buttons and featured cards.
  - `pulse-dot` — the keyframe used by "live" badge dots.
  - `card-lift` — uniform hover-lift for cards (venues, socials).
  - `text-outline` — hollow display type: the venue's name repeated as a poster texture on the venue cards that have no photo.
- `lib/data.ts` — single source of truth for the static content (hero copy, bio, formats with includes lists, venues, FAQ, socials). Sections import from here; replacing copy never touches component files. `site.genres` is the one list of styles used by the hero chips, the press kit and the JSON-LD.
- `components/sections/*` — one file per section: server components animated through `Reveal`, except the client ones listed above. `BookingForm` (inside FinalCta, anchor `#booking`) and `Contact` (anchor `#contacto`) submit to the Telegram server actions. `Venues` is a two-column grid already on mobile (six stacked cards were two screens of scroll before the music).
- `components/Navbar.tsx`, `components/Footer.tsx`, `components/StickyCta.tsx` — chrome. All anchors are **absolute** (`/#about`), because the navbar is also rendered on `/press-kit` and `/privacidad`. The desktop nav starts at `lg`: eight links plus the CTA overlapped the logo at 768 px, so a portrait tablet gets the folded menu, with the "Contratar" pill still visible from `md`. The link of the section crossing mid-screen gets `aria-current="location"` (IntersectionObserver) and "Press kit" gets `aria-current="page"` on its route. The mobile menu closes on Escape, caps its height, and the hidden StickyCta uses `invisible` so it leaves the tab order; it also hides (IntersectionObserver) while `#booking`, `#contacto` or the footer are on screen so it never covers the submit button. Form inputs are `text-base` below `md` because iOS Safari zooms into any field under 16 px.
- `public/images/` — venue photos + portrait. `public/logo-isotype.png` (black silhouette on white, no alpha channel) and `public/logo-wordmark.png` are the artist's original logos. The UI uses `logo-isotype-white.svg`, traced once from that PNG with potrace: the PNG rendered with `className="invert"` left a black square over the hero glow and the footer. `logo-isotype.svg` and `logo-isotype-{black,white}.png` (1024 px, real transparency) are the press-kit downloads. `og.jpg` is the compressed OpenGraph image.

**The gradient means "action":** `gradient-primary` is reserved for booking CTAs and `text-gradient` for the accent word of each heading. Stats figures, gig days, set durations and play buttons stay neutral (play buttons turn `bg-accent-red` on hover).

**Do not drift back to "club neon" or "editorial cinematic" aesthetics** — both were tried and rejected. The locked direction is the reference URL above. Known, accepted trade-offs of that design: white text on the red→orange gradient buttons sits below 4.5:1 on the orange end, and the hero equalizer/pulse animations are infinite (they respect `prefers-reduced-motion`). Changing either is a design decision, not a bug fix.

## Deployment

Target server: `ssh ubuntu@143.47.52.87` (aarch64/ARM, existing nginx + certbot + n8n stack). The deploy user is `ubuntu`, already in the `docker` group — no `sudo` needed, and nothing runs as `root`. **nginx runs on the host, not in Docker** — the compose publishes the container only on the loopback (`127.0.0.1:3001 -> 3000`) and nginx `proxy_pass`es to it. The image is built and stored on that same server; there is no registry.

- `Dockerfile` — multi-stage (deps → builder → runner). `node:22-alpine`, runs as non-root, executes `node server.js` from the `standalone` output.
- `docker-compose.yml` — single `web` service, no custom networks: it publishes `127.0.0.1:3001 -> 3000` so the host's nginx can reach it over the loopback. Hardened: `init: true`, `cap_drop: ALL`, `no-new-privileges`, pids/memory limits and capped json-file logs. Healthcheck against `localhost:3000` inside the container.
- `deploy/nginx-djswarthy.conf` — sample vhost: HTTP→HTTPS redirect, www → apex canonicalization, keepalive upstream, `limit_req` for the form POSTs, `proxy_pass` to the published loopback port. **Security headers live only in `next.config.ts`** (HSTS, CSP, COOP, Referrer-Policy…); nginx must not re-add them with other values.
- `deploy/README.md` — first-deploy and update walkthrough, plus the GitHub secrets the pipeline needs.
- `.github/workflows/ci.yml` — lint + typecheck + tests + `npm audit` + `next build` on every PR and non-main push. Also exposed as `workflow_call`. Both workflows run with `permissions: contents: read`.
- `.github/workflows/deploy.yml` — on push to `main`: runs CI, then SSHes into the server, `git reset --hard` to the pushed SHA, `docker compose build && up -d`, polls `/api/health`, and **rolls back to the previous commit** if the healthcheck never goes green. Deploy values travel to the remote script as positional arguments (`bash -s --`), never interpolated into the command string.

## Not yet wired

- Forms require `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` in the container environment; without them submissions fail with a generic error.
- `site.whatsapp` is empty, so the WhatsApp CTA in `FinalCta` does not render. Fill it with an international number, digits only (e.g. `34600123456`).
- `site.dates` and `site.testimonials` are empty; their sections stay hidden until real gigs/quotes are added. **Never fill them with placeholder content, not even "for a preview"** — testimonials are social proof and fake dates are emitted as `MusicEvent` schema at real venues (a demo set shipped to production once and had to be removed).
- Keeper and Samsara have no venue photo (`Venue.img` is optional and they fall back to a typographic card). The Samsara photo was deleted because it carried the club's printed logo and recognisable faces of the public. The previous image was a scanned VIP consumption card: it clashed with the rest of the grid **and carried a third party's printed name**, so it was deleted from `public/` rather than left unreferenced. Any replacement must be an actual venue photo with no personal data in frame.
- `public/images/portrait-bw.webp` and `og.jpg` are 864×1110: the bottom strip was cropped to remove a Gemini watermark. A high-resolution original without the mark is still pending; the press-kit download is labelled with its real size.
- There is no designed rider PDF: `site.press.rider` renders as HTML and the press kit prints cleanly to paper or PDF instead.
- `site.socials` has no Instagram: the handle is not known. Adding it there is enough for it to show in the footer, the socials grid and the JSON-LD `sameAs`.
- `logo-wordmark.png` is 291×173 px on a white background; a vector original of the full logo is still pending (the isotype already has an SVG).
- `SPOTIFY_CLIENT_ID` / `SPOTIFY_CLIENT_SECRET` are optional (see `.env.example`): without them the Spotify section degrades to the artist profile player instead of the album grid. Adding a new embed host means widening `frame-src` in the CSP **and** `images.remotePatterns` in `next.config.ts`.
